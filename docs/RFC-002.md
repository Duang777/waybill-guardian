- 作者：Duang777

## 摘要

RFC-001 证明了异常运单处置的核心链路：Agent 查询证据、提出方案、等待人工审批，再执行
TMS 和通知写操作。当前实现适合离线演示，不适合连接真实平台。它依赖单进程内存锁和本地
JSONL，缺少调用方身份、跨进程协调、真实事件入口，以及外部写入未知结果的对账能力。

本 RFC 选择渐进式生产化方案：

1. 用 PostgreSQL 保存业务状态、审批、effect、审计事件、inbox 和 outbox。
2. 用 CloudEvents 1.0 信封接收异常事件，以 `source + id` 去重。
3. 在内部事件模型中保留 EPCIS 的 what、when、where、why、how 五类语义，但不要求上游
   直接实现完整 EPCIS 2.0。
4. hastekit 继续负责 Agent 推理和工具调用。`guardian` 负责确定性的业务状态机、权限、
   effect 身份和恢复。
5. 写操作通过持久化 effect worker 执行。未知结果只能按幂等键查询，不能直接重试。
6. 用 transactional outbox 发布状态变化。下游按 at-least-once 接收，并通过 inbox 去重。
7. 审计事件与 OpenTelemetry 各司其职。前者回答谁批准了什么，后者回答一次调用在哪里变慢
   或失败。

第一阶段不引入 Temporal。PostgreSQL、租约和 outbox 已能解决当前规模的恢复与多实例协调，
同时保留现有 Go 模块和 hastekit 接入。只有在长时间审批、复杂补偿和工作流数量超过自研状态机
的维护能力时，才迁移到 Temporal。

## 背景

项目服务于延误、破损和丢件后的处置。完整业务过程不止于一次模型调用：

```text
异常事件
  -> 去重和归一化
  -> 创建或合并事故
  -> 拉取运输证据
  -> Agent 归因和提案
  -> 策略校验
  -> 人工审批
  -> TMS、理赔和通知写回
  -> 对账
  -> 关闭事故
  -> 复盘和评测
```

真实系统中的主要风险发生在边界上：

- 上游会重复投递、乱序投递或补发历史事件。
- 审批可能持续数小时，期间会发生重启、发布和人员交接。
- 外部平台可能已经提交写入，但客户端只收到超时。
- 一个审批批次可能部分成功，不能整体标记为完成。
- 模型输出、工具参数和审批人身份来自不同信任域。
- 审计记录需要长期保留，运行日志和模型输入则需要最小化采集。

## 目标

本 RFC 规定从异常事件进入系统，到所有外部 effect 得到确定结果的生产链路。

系统需要满足：

- 相同异常事件重复投递时，只创建一个逻辑事故。
- 任意服务实例可以接手未完成 run，不依赖原进程内存。
- 审批决定绑定提案版本、完整参数哈希、策略版本和操作者身份。
- 每个外部 effect 都有服务端生成的稳定身份和幂等键。
- 网络超时后，系统能区分确定失败与未知结果。
- 单个 run 的损坏或对账阻塞不能阻止服务启动。
- 审计回放可以还原当时可见的证据、提案、决定和执行结果。
- 日志、追踪和模型历史默认不保存不必要的个人信息。

## 非目标

- 不在本阶段实现通用物流主数据平台。
- 不要求所有上游和下游原生支持 EPCIS。
- 不承诺跨外部 TMS、短信平台和本地数据库的 exactly-once 事务。
- 不让大模型决定权限、幂等键、重试策略或最终业务状态。
- 不在第一阶段引入多 Agent 协作、自动赔付或无人审批写入。
- 不把 OpenTelemetry trace 当作合规审计记录。

## 现状与差距

当前实现已经具备可复用的业务骨架：

| 能力 | 当前实现 | 生产差距 |
|---|---|---|
| Agent 执行 | hastekit file history 和 pause/resume | history 含明文业务数据，且只适合单机 |
| 审批 | JSONL 投影和进程内定时器 | 无认证、无角色、截止时间存在竞态 |
| 幂等 | 进程内 map 与审计事件重建 | 外部超时被当成失败，缺少按 key 对账 |
| 审计 | 每个 run 一份哈希链 JSONL | 无多 writer、保留策略、签名根或归档 |
| 事件入口 | 手工触发固定 demo | 无真实异常事件、去重、乱序和修正语义 |
| 外部平台 | fixture mock | real adapter 明确未实现 |
| SSE | replay 加 live | 无身份校验，慢客户端缺少写截止时间 |
| 运维 | 本地脚本 | 无 CI、指标、告警、容量基线和故障隔离 |

[#28](https://github.com/Duang777/waybill-guardian/issues/28) 记录了第一轮审计发现。真实 adapter
开始开发前，必须先修复 P0 和 P1 缺陷。

## 调研结论

### 运输事件采用兼容层，不强制上游改造

GS1 EPCIS 2.0 用 what、when、where、why、how 描述供应链可见性事件，并区分
`eventTime` 与 `recordTime`。它还定义只追加的错误声明，而不是原地改写历史事件。该模型适合
运输轨迹和异常证据，但完整 EPCIS 对现阶段上游要求过高。

系统内部保留这些语义，并提供 source-specific adapter。合作方已经支持 EPCIS 时，adapter
直接映射 EPCIS JSON-LD。其他来源可以发送较小的本地 schema。

### 事件信封采用 CloudEvents 1.0

CloudEvents 1.0 要求 `id`、`source`、`specversion` 和 `type`。生产者必须保证
`source + id` 唯一，消费者可以把同一组合视为重复事件。该规则可以直接作为 inbox 主键。

CloudEvents 只规定事件上下文，不规定运输业务字段。业务 payload 仍由本项目版本化。

### 内部状态和待发布事件必须同事务提交

AWS 的 transactional outbox 文档把数据库更新后发消息描述为 dual write 问题。数据库提交
成功但消息发送失败，或数据库回滚但消息已经发送，都会造成不一致。推荐做法是在同一数据库
事务中写业务状态和 outbox，再由 dispatcher 发送。

outbox 只能保证事件不丢。消费者仍可能收到重复消息，因此每个消费者都需要 inbox 或等价的
幂等记录。

### 外部写入采用 effectively-once

消息系统通常提供 at-least-once，而不是覆盖外部副作用的 exactly-once。Azure 的
Idempotent Consumer 模式要求使用稳定业务标识、原子 claim 和唯一约束，并把幂等键继续传给
下游。

Stripe 的公开 API 还提供两个有用约束：同一幂等键重放首次结果，参数不一致时返回冲突。该
语义比只保存“成功过”更完整。本项目应保存请求哈希、状态码、响应体摘要和外部引用。

### 持久化审批可以先用数据库状态机

Temporal 的人工审批指南说明了持久化 wait、signal、durable timer 和历史 replay 的价值。
它也要求工作流逻辑保持确定性，并管理事件历史大小。当前项目已经用 hastekit 保存模型运行
历史，再引入 Temporal 会形成两套工作流历史和两个恢复入口。

本阶段用 PostgreSQL 状态机、租约和定时扫描解决审批等待。满足以下任一条件后再评估 Temporal：

- 单个流程需要跨越数天，并包含多级审批、提醒、升级和反复补件。
- 状态机分支持续增加，补偿逻辑难以通过数据库约束表达。
- worker 部署和恢复代码的维护成本高于独立工作流平台。
- 业务需要可视化工作流运维、版本迁移和跨服务 durable timer。

### 审计与可观测性分开

OpenTelemetry 的 GenAI 语义约定定义了 `invoke_agent`、`invoke_workflow`、`plan` 和
`execute_tool` 等 span，但截至本 RFC 修订日期仍处于 Development。系统可以采用这些名称，
同时在自有命名空间保留稳定字段。

模型输入、输出、系统指令和工具定义可能包含个人信息。相关 OpenTelemetry 字段保持 opt-in，
生产默认只记录标识、耗时、token 数、错误类型和结果状态。

NIST AI RMF 要求明确人机职责、持续监控、第三方风险和人工监督。审批角色、模型版本、策略版本、
回滚入口和评测结果因此属于上线材料，不是运行时附加信息。

## 目标架构

```text
TMS / GPS / IoT / 客服事件
          |
          v
  ingestion API or consumer
  - authenticate source
  - validate CloudEvent
  - inbox deduplicate
  - normalize payload
          |
          v
  PostgreSQL
  - incidents / runs / evidence
  - proposals / approvals / effects
  - audit_events / inbox / outbox
          |
          +-----------------------+
          |                       |
          v                       v
  guardian workers         outbox dispatcher
  - claim run lease        - publish domain events
  - call hastekit          - notify approvers
  - validate proposal      - update read models
          |
          v
  approval API and console
  - authenticated operator
  - version-bound decision
          |
          v
  effect workers
  - durable claim
  - call external adapter
  - query unknown result
          |
          v
  TMS / claim / notification platforms

  audit_events -> audit export and replay
  OpenTelemetry -> traces, metrics and alerts
```

PostgreSQL 是业务状态的唯一权威来源。SSE、列表页和详情页都读取数据库投影。hastekit history
只保存恢复 Agent 所需的最小上下文，不承担审批、effect 或审计事实。

### Agent checkpoint

生产模式实现 PostgreSQL 版本的 hastekit `ConversationPersistenceAdapter`。checkpoint 按
`tenant_id + namespace + thread_id + sdk_run_id` 保存，消息只追加，并使用唯一约束拒绝重复
记录。数据库列使用服务端加密，写入前执行字段级脱敏。

`runs` 保存 `sdk_run_id` 和 `checkpoint_version`。worker 获得 run 租约后，按该版本恢复 Agent。
hastekit checkpoint 与业务状态不能假装成一个原子事务，恢复流程按以下顺序处理：

1. hastekit 先保存 checkpoint，再向 `guardian` 返回 paused 或 completed。
2. `guardian` 在一个事务中保存提案、审批、业务审计和所消费的 `checkpoint_version`。
3. checkpoint 已保存但业务事务未提交时，新 worker 读取未消费版本，并幂等地重建同一提案。
4. 业务记录引用不存在的 checkpoint，或 checkpoint 内容与参数哈希不一致时，run 进入
   `manual_review`，其他 run 继续恢复。

不同实例不能使用本地 file history 接管同一 run。`PLATFORM=real` 时，file history 配置属于
启动错误。

## 事件入口

### CloudEvents 信封

入口接受结构化 CloudEvents JSON：

```json
{
  "specversion": "1.0",
  "id": "evt-20261010-000184",
  "source": "urn:tms:region-east",
  "type": "com.waybill.tracking.delay.detected.v1",
  "subject": "waybill/YD2026101001",
  "time": "2026-10-10T12:30:00Z",
  "datacontenttype": "application/json",
  "dataschema": "https://example.invalid/schemas/waybill-delay-v1.json",
  "data": {
    "waybill_id": "YD2026101001",
    "event_time": "2026-10-10T12:28:31Z",
    "record_time": "2026-10-10T12:30:00Z",
    "location": {"code": "MY-N-SERVICE", "name": "绵阳北服务区"},
    "business_step": "transporting",
    "reason_code": "stop_duration_exceeded",
    "observations": {"stop_minutes": 360}
  }
}
```

入口事务执行以下操作：

1. 验证来源身份、schema 版本、大小和时间字段。
2. 以 `(tenant_id, source, id)` 插入 `inbox_events`。
3. 重复键返回原接收结果，不重复创建事故。
4. 将来源 payload 映射为 `TransportEvent`。
5. 创建或更新事故，并追加 `incident.detected` outbox 事件。
6. 提交事务后返回 `202 Accepted` 和内部 `incident_id`。

事件的发生时间和接收时间分别保存。乱序事件按业务版本和发生时间投影，不能按到达顺序覆盖较新
状态。上游修正使用新事件引用被修正的 `source + id`，不修改原始 inbox 记录。

## Agent 与策略边界

hastekit 负责读取证据、生成归因和提出候选动作。它不负责以下决定：

- 是否允许某个调用方查看运单。
- 哪个角色可以批准某类动作。
- effect ID 和幂等键如何生成。
- 网络错误是否可以重试。
- run 是否已经完成。

Agent 输出变为 `ActionProposal`，其中只包含业务参数：

```go
type ActionProposal struct {
	Action       domain.Action
	Target       string
	Arguments    json.RawMessage
	EvidenceRefs []domain.EvidenceID
	Reason       string
}
```

服务端在 schema 校验和策略评估后生成：

```text
proposal_id
proposal_version
arguments_hash
policy_version
effect_id
idempotency_key
```

模型不再生成或回显 `idempotency_key`。执行契约与 Agent 工具契约分开，避免模型把安全字段当作
普通参数修改。

策略层先使用确定性 Go 规则。规则输入包括动作类型、参数、货值、租户策略、风险等级和证据新鲜度。
模型可以解释规则结果，但不能覆盖规则。

## 审批

审批状态机为：

```text
pending -> confirmed -> executing -> executed
        |             |            |-> partially_failed
        |             |            `-> reconciliation_required
        |             `-> superseded
        |-> rejected
        `-> expired
```

每个审批必须保存：

- 租户、事故、run、提案版本和 effect 列表。
- 完整参数哈希和展示用脱敏参数。
- 证据引用及其采集时间。
- 模型、prompt、工具契约和策略版本。
- 需要的角色、审批人数和职责分离规则。
- 截止时间、决定人、决定时间和原因。

确认请求携带 approval version。数据库事务锁定审批行，同时检查状态、版本和 `expires_at`。
服务端从认证上下文写入 `decided_by`。请求头不能指定审批人。

审批决定与 effect 准备记录在同一事务中。事务提交后，effect worker 才能执行外部写入。重复确认
返回第一次决定。参数、版本或决定冲突返回 `409 Conflict`。

高风险动作可以配置双人审批。首个审批人不能满足第二个审批槽位。该规则属于租户策略，不交给
Agent 判断。

## Effect 执行与对账

### 稳定身份

服务端按逻辑 effect 生成 ID：

```text
effect_id = UUIDv5(
  tenant_id |
  proposal_id |
  proposal_item_id
)
```

服务端根据 `action + target + canonical_arguments_hash` 生成 `proposal_item_id`。同一提案中
完全相同的两项视为重复并拒绝，目标或参数不同的同类动作得到不同 ID。`proposal_id` 跨 run
唯一，因此新 run 不会复用旧 effect。

当前 `action + waybill_id + business_window` 不能区分同一方案中的两个
`notify.send_sms`。

对支持客户端幂等键的平台，`idempotency_key` 使用 `effect_id` 的稳定编码。重试和对账始终使用
同一个 key。

阶段 A 在尚未引入 tenant 表和 proposal 表时，先落地同一规则的 `effect-v1` 实现：

```text
proposal_id = UUIDv5(
  proposal_namespace,
  canonical_json(run_id, incident_id, waybill_id, plan_version)
)
proposal_item_id = SHA256(canonical_json(
  identity_version,
  action,
  server_derived_target,
  canonical_business_arguments_hash
))
effect_id = UUIDv5(
  effect_namespace,
  canonical_json(proposal_id, proposal_item_id)
)
idempotency_key = SHA256("waybill-effect-key-v1\0" + effect_id)
```

`call_id` 只关联 hastekit 的 pending call、审批 resolution 和工具结果，不进入上述计算。
服务端在 `approval_requested` 落盘前生成并保存 effect 身份。模型可见的工具 schema 只包含
业务参数。effect middleware 在批准执行时重算身份，并通过可信 execution context 把 key
传给 typed handler。

阶段 A 保持审计 envelope 的 `schema_version: 1` 和现有哈希算法。新 payload 增加
`identity_version`、`effect_id` 和 `attempt`。确定失败后的每次重试使用新的 attempt 事件 ID，
防止 append-only 去重返回旧事件。

旧审批项缺少新身份字段时，系统保留原 `idempotency_key` 和完整参数哈希。已有成功结果只回放。
未完成的旧审批若有多个 item 共用同一 key，系统在调用外部平台前把该 run 转入人工处理，不能
为脱敏后的旧参数补算新 key。

兼容分支还读取 PR #45 产生的 `effect-v0` 记录。这类记录有 `effect_id`，但没有
`identity_version` 和 `attempt`。恢复时使用已发布的 v0 算法校验 effect 和 key；所有新写入使用
`effect-v1`。

### 状态机

```text
prepared -> dispatching -> succeeded
                       |-> retryable_failed -> dispatching
                       |-> permanent_failed
                       `-> unknown -> reconciling -> succeeded
                                                |-> retryable_failed
                                                `-> manual_review
```

adapter 返回结构化结果：

```go
type EffectResult struct {
	Disposition EffectDisposition
	ExternalRef string
	Response    json.RawMessage
	RetryAfter  time.Duration
}

type EffectDisposition string

const (
	EffectSucceeded       EffectDisposition = "succeeded"
	EffectRetryableFailed EffectDisposition = "retryable_failed"
	EffectPermanentFailed EffectDisposition = "permanent_failed"
	EffectUnknown         EffectDisposition = "unknown"
)
```

连接超时、连接重置和响应解析失败默认是 `unknown`，因为服务端可能已经提交。`unknown` 只调用
`LookupEffect(idempotency_key)`。adapter 明确返回未执行后，状态才能进入
`retryable_failed`。

审批只有在所有 effect 为 `succeeded` 时进入 `executed`。任一 effect 为
`permanent_failed` 时进入 `partially_failed`。存在 `unknown` 时进入
`reconciliation_required`。run 的最终状态必须由 effect 投影计算，不能采用模型的 completed
文本。

### 租约与并发

worker 使用数据库租约 claim run 和 effect。claim 操作必须是单条原子 SQL，或在事务中使用
`SELECT ... FOR UPDATE SKIP LOCKED`。租约包含 owner、deadline 和 fencing token。

每次状态更新都校验 fencing token。旧 worker 在暂停后恢复时，不能覆盖新 owner 已提交的结果。
worker 在执行外部调用期间续租。续租失败后停止领取和发起新调用。调用前在数据库事务中再次校验
fencing token，并确保调用超时短于剩余租期。

fencing token 只能保护数据库写入，不能撤回已经发出的网络请求。生产 adapter 必须同时满足：

- mutation 接受幂等键，同 key 和同参数返回第一次结果。
- 同 key 和不同参数返回冲突。
- 提供按 key 查询结果的接口，或保证重放同 key 可以返回已提交结果。
- 区分确定失败、可重试失败和未知结果。
- 通过超时、断连、并发重放和进程终止的 contract test。

不满足该能力矩阵的 adapter 只能用于只读或 sandbox 模式。数据库唯一约束负责裁决 inbox ID、
effect ID、审批版本和每个 run 的审计序号。

## Outbox 与下游事件

所有需要发给其他系统的状态变化先写入 `outbox_events`，并与业务状态放在同一事务中。dispatcher
按序 claim、发布并记录结果。

事件继续使用 CloudEvents 信封。首批事件包括：

- `com.waybill.incident.detected.v1`
- `com.waybill.run.awaiting-approval.v1`
- `com.waybill.approval.decided.v1`
- `com.waybill.effect.succeeded.v1`
- `com.waybill.effect.reconciliation-required.v1`
- `com.waybill.incident.resolved.v1`

发布保证是 at-least-once。`source + id` 在所有重发中保持不变。每个消费者按
`consumer_id + source + id` 建立 inbox，不能把 broker 的 delivery ID 当作业务去重键。

同一 incident 的事件携带 `incident_version`。消费者拒绝旧版本覆盖新版本。系统不提供跨 incident
的全局顺序保证。

## 数据模型

建议的最小表如下：

| 表 | 用途 | 关键约束 |
|---|---|---|
| `inbox_events` | 保存原始入站事件和处理结果 | unique tenant, source, event_id |
| `incidents` | 异常业务聚合 | unique tenant, source incident key |
| `runs` | 一次调查和处置尝试 | lease owner, deadline, fencing token |
| `evidence_snapshots` | 保存带来源和采集时间的证据 | immutable payload hash |
| `proposals` | 保存 Agent 候选方案 | unique run, proposal version |
| `approvals` | 保存人工作出的决定 | optimistic version |
| `approval_effects` | 固定审批包含的 effect 集合 | unique approval, effect |
| `effects` | 外部写入和对账状态 | unique tenant, effect_id |
| `agent_checkpoints` | 保存 hastekit 消息和 run state | unique tenant, thread, sdk run |
| `audit_events` | 业务审计事实 | unique run, seq and event_id |
| `outbox_events` | 待发布领域事件 | unique source, event_id |

审计 payload 在写入前按 schema 脱敏。个人信息保存在独立受控表中，审计只保存不可逆的业务
引用。删除个人信息时删除引用映射或对应加密密钥，不改写审计事件。

数据库保存每个 run 的哈希链。run 关闭后不得继续追加事件，后续修正创建关联的 correction run。
封存任务为每个关闭 run 生成 manifest，内容包括 tenant、run ID、事件数、末端 seq、末端 hash
和封存时间。KMS 对 manifest 签名，再将 manifest 写入启用 object lock 和保留期的对象存储。
验证工具检查事件链、manifest 签名、对象保留状态和数据库中的关闭 run 清单，从而发现单条篡改、
截断和整份 run 删除。

## API

第一版生产 API：

```text
POST /v1/events
GET  /v1/incidents/{incident_id}
POST /v1/incidents/{incident_id}/runs
GET  /v1/runs?status={status}
GET  /v1/runs/{run_id}
GET  /v1/runs/{run_id}/timeline?after={seq}
GET  /v1/approvals?status=pending
POST /v1/approvals/{approval_id}/decisions
GET  /v1/effects?status={status}
GET  /v1/effects/{effect_id}
POST /v1/effects/{effect_id}/reconcile
```

所有端点验证 tenant 和资源归属。审批端点要求审批角色。手工对账端点要求运维角色，并记录原因。

`POST /decisions` 接受：

```json
{
  "approval_version": 3,
  "decision": "confirm",
  "reason": "证据完整，承运商容量已复核"
}
```

客户端为 mutation 请求发送请求幂等键。该 key 只去重 API 请求，不替代 effect ID。

run snapshot 在同一个数据库快照中返回当前投影和 `last_seq`。客户端先读取 snapshot，再用
`?after={last_seq}` 建立 SSE。服务端先回放更大的 seq，再切换到 live，因此查询与订阅之间提交
的事件不会丢失。后续断线使用 `Last-Event-ID` 重连。

控制台启动时先读取活跃 run 和待审批列表，再订阅选中 run 的时间线。浏览器内存中的
`run_id` 不能成为恢复入口。运维视图还要查询 `reconciliation_required` 和
`manual_review` effect。handler 为每次 SSE 写入设置截止时间。

## 故障处理

| 故障点 | 恢复行为 |
|---|---|
| inbox 提交前崩溃 | 上游重发，重新处理 |
| inbox 与 incident 提交后、响应前崩溃 | 重发命中 inbox，返回原 incident |
| proposal 已保存、通知未发送 | outbox dispatcher 重发通知 |
| 审批决定已提交、worker 未执行 | 其他 worker 在租约到期后接手 |
| 外部请求发送前失败 | 进入 retryable_failed |
| 外部请求发送后超时 | 进入 unknown，只做按 key 对账 |
| 外部成功、结果写库前崩溃 | 重启后按相同 key 对账 |
| 批次部分成功 | 保留单项结果，审批进入 partially_failed |
| 单个 run 数据损坏 | 隔离该 run，服务继续启动并告警 |
| outbox 发布后、标记前崩溃 | 重发同一 CloudEvent ID，消费者去重 |
| SSE 客户端断开 | 按持久化 seq 补发 |

恢复流程不能把待对账状态改成通用 `failed`。运维页面必须列出
`reconciliation_required` 和 `manual_review`，并显示最后一次外部请求的时间、adapter、
idempotency key 摘要和错误分类。

## 可观测性与评测

每个入站请求建立 trace，并传播以下关联字段：

- `tenant_id`
- `incident_id`
- `run_id`
- `approval_id`
- `effect_id`
- `cloudevent.id`

Agent 相关 span 采用 OpenTelemetry GenAI 当前定义的操作名，但通过版本化 instrumentation
封装，避免 Development 状态的字段直接散布在业务代码中。

默认指标包括：

- 入站事件接收量、重复率和 schema 拒绝率。
- run 从创建到待审批的耗时。
- 审批等待时间、过期率和驳回率。
- effect 成功率、重试率、unknown 数量和对账时长。
- outbox backlog、最老未发布事件年龄和发布失败率。
- Agent 调用耗时、错误、token 数和工具调用次数。

模型输入、模型输出和工具参数默认不进入 trace。需要采样时，先经过与审计相同的字段级脱敏，并
设置独立保留期。

离线评测固定输入事件和平台快照，比较归因、证据引用、提案合法性和是否触发正确审批。线上只评估
建议质量，不让评估器改变业务结果。

## 安全与隐私

- 服务使用统一身份入口。操作者、事件生产者和服务账号使用不同凭据。
- 授权至少包含 tenant、资源、动作和角色。前端隐藏按钮不能代替服务端授权。
- LLM 输出按不可信输入处理。所有工具参数都经过 schema、业务规则和审批绑定。
- 调用模型前删除手机号、车牌和精确轨迹等非必要字段。
- 模型凭据和 adapter 凭据存入 secret manager，并使用最小权限。
- 审计、模型历史、trace 和业务表使用不同保留期。
- 数据导出、手工对账、策略修改和权限修改都生成审计事件。
- 生产启动检查拒绝 `PLATFORM=real` 与无认证、无加密存储或无对账能力的组合。

## 迁移顺序

### 阶段 A：修正当前安全和一致性缺陷

完成 [#16](https://github.com/Duang777/waybill-guardian/issues/16) 至
[#28](https://github.com/Duang777/waybill-guardian/issues/28) 中的 P0 和 P1 项。保持 mock
演示行为不变。JSONL 模式还要持有 `DATA_DIR` 独占锁，避免两个 demo 进程同时写入。

### 阶段 B：建立 PostgreSQL 事实源

加入 schema migration、事务仓储、inbox、outbox、run lease 和 effect 状态机。先让 demo
adapter 在数据库路径上通过相同 E2E，再移除业务 JSONL 写入。

### 阶段 C：接入一个只读真实来源

先接 TMS 运单和轨迹查询，不开放写操作。保存来源快照、延迟、错误类型和数据新鲜度，校准归因
规则。

### 阶段 D：接入一个可查询结果的写操作

优先接支持幂等键和按 key 查询的通知或 TMS sandbox。完成超时、断连、重复响应和服务重启的
故障注入测试后，才启用真实审批执行。

### 阶段 E：补齐运营能力

加入权限、待审批队列、待对账队列、指标、告警、审计导出和模型评测。完成容量测试后再决定 worker
数量和租约时长。

### 阶段 F：重新评估工作流平台

收集三类数据：平均流程时长、每个 run 的状态转换数、状态机和恢复代码的维护成本。达到本 RFC
前述条件时，写独立 RFC 评估 Temporal。迁移时由一个系统拥有 workflow 状态，不能让 Temporal
和 `guardian` 同时成为权威来源。

## 验收标准

生产写模式必须通过以下验证：

1. 同一 CloudEvent 并发提交十次，只创建一个 incident。
2. 两个 worker 同时 claim 同一 run 或 effect，只有一个 fencing token 可以提交结果。
3. 在每个事务边界执行 kill 后，重启可以继续处理，且服务不会因单个 run 失败而退出。
4. 外部平台成功但客户端超时后，系统只查询结果，不盲目重试。
5. 批次中一个 effect 成功、一个失败时，审批不会进入 executed。
6. 审批到期后，即使确认请求与定时任务并发，写操作也不会执行。
7. 匿名、跨 tenant 和缺少审批角色的请求不能读取或决定资源。
8. 持久化文件、数据库导出和 trace 中不出现策略禁止的明文个人信息。
9. outbox 重复投递不会让消费者重复改变状态。
10. 审计回放在任意 seq 都显示该时刻一致的 run、审批和 effect 状态。
11. 任意实例可以从 PostgreSQL checkpoint 接管 paused run，本地磁盘为空不影响恢复。
12. 审计验证工具能发现事件改写、尾部截断、整份 run 删除和伪造 manifest。
13. 真实模式缺少任一 adapter 能力或数据保留配置时，服务拒绝启动。

测试采用真实 PostgreSQL 和 adapter contract test。mock 单测不能替代进程终止、网络超时和多
worker 竞争测试。

## 备选方案

### 继续使用 JSONL 和单进程锁

该方案最少改动，但无法提供跨进程 claim、数据库事务、查询索引和稳定的运营接口。它继续保留为
离线 demo 模式，不进入真实写路径。

### 立即迁移到 Temporal

Temporal 原生支持 durable wait、signal、timer 和 replay，适合长时间审批。当前系统的业务流程
还较短，引入 Temporal 会同时维护 hastekit history、Temporal history 和业务审计。现阶段成本
高于收益，因此延后到有运行数据时再决定。

### 让消息队列成为业务事实源

消息队列适合传递事件，不适合直接承载审批查询、参数版本、对象级授权和人工对账。数据库仍需保存
这些状态，队列只处理分发。

### 要求所有合作方实现 EPCIS

EPCIS 的语义完整，但现有 TMS、GPS 和天气接口未必使用 EPC 标识或 JSON-LD。内部兼容模型加
adapter 可以保留标准语义，也能控制首个接入范围。

## 待确认事项

- 首个真实 TMS 是否支持客户端幂等键和按 key 查询结果。
- 企业身份源、tenant 模型和审批角色的实际接口。
- 审计和模型历史的具体保留时长。生产配置必须显式填写时长、加密密钥和归档目标。
- 首批异常事件来自 webhook、消息队列还是轮询。
- 赔付动作需要单人审批、双人审批还是金额分级。
- 生产流量和审批时长分布，用于确定容量目标和 Temporal 评估时点。

这些信息不会阻止阶段 A 和阶段 B。它们会阻止真实写模式上线。
