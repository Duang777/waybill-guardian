# RFC-001：异常运单自治处置 Agent 架构设计

- 状态：草案
- 作者：Duang777
- 日期：2026-10-03
- 关联：`AGENTS.md`（根）、`contract.yaml`、各目录 `AGENTS.md`

## 1. 背景与目标

「AI 重构产业 · 架构师大赛」AI+物流赛道。物流异常（延误 / 破损 / 丢件）发生后，
传统流程靠人工逐单排查：查运单、看轨迹、联系司机、看天气，再决定改派还是赔付。
本项目用 Agent 把"排查 → 归因 → 出方案"自动化，**把"执行"留在人工手里**。

目标（初赛 48h 可交付）：

1. 异常触发后，Agent 自动完成归因并生成处置方案（改派 / 赔付 / 通知）。
2. 所有写操作必须经过人工确认闸；确认后回写 TMS（初赛为 mock）。
3. 全程审计可回放；3 分钟 demo 讲清"异常 → 归因 → 审批 → 回写"。

## 2. 非目标

- 不做完整 TMS（无真实接口前不造大而全的平台）。
- 不做通用调度求解（OR-Tools 只作为"候选运力选择"的备选工具，不单独成产品）。
- 初赛不做多租户、权限体系、生产级可观测。

## 3. 总体架构

```
web/  (React + 高德 JS API)
 ├─ 异常运单地图 / 轨迹回放
 ├─ Agent 审计时间线
 └─ 人工审批卡片
        │ HTTP + SSE
cmd/server ── internal/agent  (hastekit v0.0.24，钉死版本)
                 ├─ tools:       7 个契约工具（查询自动执行，写操作走审批）
                 ├─ approval:    人审闸 pending → confirmed / rejected / expired
                 ├─ idempotency: 写操作强制 idempotency_key（middleware 拦截缺键）
                 ├─ audit:       append-only 事件流，可回放
                 └─ platform:    mock TMS ⟷ 真实 adapter（同一 Go interface）
```

数据流（一句话）：异常事件 → agent run → 只读工具自动执行（归因）→
写操作被 middleware 拦截生成审批单 → 人工确认 → 执行并记审计 → SSE 推送前端。

## 4. 工具契约

见 `contract.yaml`（冻结版）。两条铁律：

1. 查询类工具可自动执行；`tms.reassign` / `tms.create_claim` / `notify.send_sms`
   必须经过人工确认。
2. 写操作强制携带 `idempotency_key`，缺键在 middleware 层直接拒绝。

## 5. 核心设计决策

### D1. Harness 选 hastekit/agent-sdk-go（v0.0.24 钉死）

- 备选：纯自研 Go harness、Dify/n8n 平台。
- 依据：Go 原生，function calling/MCP、provider 抽象、retry/fallback middleware、
  HITL、流式事件齐备；脏活 80% 现成，自研聚焦人审/幂等/审计 20%。
  Dify/n8n 组装最快，但"架构师大赛"下技术叙事塌掉（详见选型记录）。
- 风险：项目新（12 stars）、声明有 breaking changes → 钉死版本；HITL 语义待源码验证（Issue #R1）。

### D2. 人审闸为同步阻塞，而非事后审计

- 备选：先执行、事后审计告警。
- 依据：改派涉及真实运力，不可逆；事后审计拦不住已发出的指令。
  这是评委必问 Q2（"怎么防 Agent 改错"）的正面回答。

### D3. 幂等放在 middleware 层强制，而非每个 tool 自觉

- 依据：agent 场景天然多重试（模型重试、fallback、人工重复点击），
  靠调用方自觉一定会漏；middleware 拦截是架构级保障。

### D4. 审计 append-only + 哈希链，可回放

- 依据：支撑"事故复盘"演示；评委可回放处置全过程；哈希链为决赛"防篡改"叙事留口子。

### D5. Platform seam：mock 与真实 adapter 同一 interface

- 依据：赛前无真实接口；interface 隔离变化，真实接口就绪后新增 adapter 文件即可，
  agent/tools 零改动。

### D6. 前端地图用高德 JS API

- 依据：演示在国内，Leaflet/CARTO 瓦片可能慢；高德稳定。Key 放 `.env.local` 不提交。

## 6. 人审闸详细设计

状态机：`pending → confirmed → executed`；`pending → rejected`（需驳回原因）；
`pending → expired`（超时默认拒绝，演示配置 10 分钟）。

审批单字段：`id / run_id / waybill_id / action / params（含 idempotency_key）/`
`reason（处置理由）/ evidence（归因证据链摘要）/ status / decided_by / decided_at / reject_reason`。

与 hastekit HITL 的对接取决于 Issue #R1 的结论：

- 若 SDK 支持持久化 pause/resume：直接对接。
- 若仅同步回调：本状态机为权威——审批单落盘，run 挂起等待，前端确认后恢复。

## 7. 幂等设计

Key 生成：`sha256(action + "|" + waybill_id + "|" + business_window)`，
`business_window` 为业务时间窗（同一异常事件 id），同一异常的重复处置视为同一操作。

语义：首次执行并存储 `key → result`；同 key 重复请求不重新执行，直接返回首次结果，
并记 `duplicate_suppressed` 审计事件。存储初期内存 map + JSONL，接口预留迁 SQLite。

## 8. 审计设计

事件模型：`seq（单调递增）/ ts / run_id / actor（agent|human|system）/ type / payload / prev_hash`。
事件类型：`tool_call / tool_result / attribution / approval_requested /`
`approval_decided / write_executed / note / duplicate_suppressed`。

存储：`data/audit-<run_id>.jsonl`，只追加；不提供 update/delete API，
错误用补偿事件表达。回放：`Replay(run_id)` 按 seq 重放，供前端时间线与 SSE 断线续传
（`Last-Event-ID = seq`）使用。敏感字段（司机电话、车牌）脱敏后记入。

## 9. Platform seam 设计

```go
type TMSClient interface {
    GetWaybill(waybillID string) (*Waybill, error)
    GetTracking(waybillID string) ([]TrackPoint, error)
    GetDriver(driverID string) (*Driver, error)
    Reassign(waybillID, carrierID, idempotencyKey string) (*ReassignOrder, error)
    CreateClaim(waybillID, claimType, idempotencyKey string) (*ClaimOrder, error)
}
```

`MockTMS` 由 `internal/tools/testdata/demo.json` 驱动（确定性演示数据）；
`RealTMSAdapter` 待真实接口就绪后新增文件实现；`PLATFORM=mock|real` 环境变量切换。
天气独立 `WeatherClient` interface，mock 返回"成绵高速段晴、无预警"
（**有意设计**：演示时 agent 能说出"已排除天气因素"，体现归因严谨）。

## 10. 前端设计

四块：异常运单地图（轨迹线 + 绵阳异常点高亮，点击轨迹点看时间/速度）、
审计时间线（消费 SSE，实时追加）、审批卡片（方案 + 证据链 + 确认/驳回，
信息密度优先、一屏看完）、风险评分条（三段式装饰）+ 回放控制条。

时间线是审计的投影，不维护独立状态；断线用 `Last-Event-ID` 续传。

## 11. 演示剧本（初赛视频）

运单 YD2026101001，杭州 → 成都，时效 72h：

1. 车辆在绵阳段停留 6h（异常触发）。
2. Agent 自动执行：`get_waybill` → `get_tracking` → `get_driver`（连续驾驶 9h、疲劳预警）
   → `get_road_weather`（晴、无预警，排除天气）。
3. 归因结论："司机疲劳驾驶 + 服务区长时间停留"，证据链上屏。
4. 生成改派方案（候选运力二选一）→ 审批卡片弹出 → 人工确认。
5. 回写 TMS（mock 返回改派单号）→ 短信通知货主（mock 记日志）。
6. 审计时间线回放，全程 3 分钟内讲完。

## 12. 风险与待验证项

| 风险 | 缓解 |
|---|---|
| hastekit HITL 语义不明（同步回调 vs 持久化挂起） | Issue #R1 源码验证；已预留状态机兜底 |
| hastekit breaking changes | 钉死 v0.0.24；升级需手动回归 |
| 国内 OpenAI-compatible endpoint 接入 | Issue #D2 验证 base_url 配置并文档化 |
| 48h 内联调风险 | 演示数据确定性；mock 写操作无真实副作用 |
