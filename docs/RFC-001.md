# RFC-001：异常运单自治处置 Agent 架构设计

- 状态：演示基线已完成，生产化加固进行中
- 作者：Duang777
- 修订日期：2026-10-03
- 关联：`AGENTS.md`、`contract.yaml`、各目录 `AGENTS.md`
- 研究记录：[`docs/research/hastekit-v0.0.24.md`](./research/hastekit-v0.0.24.md)

## 1. 背景与目标

物流异常发生后，传统流程靠人工逐单查询运单、轨迹、司机和天气，再决定改派、赔付或通知。
本项目用 Agent 自动调查并生成方案，但把外部写操作的最终决定留给人工。

初赛交付必须满足以下目标：

1. 异常触发后，Agent 自动完成归因并生成处置方案。
2. 所有写操作在执行前都必须获得人工确认。
3. 模型重试、恢复重放和重复点击不能产生重复副作用。
4. 审计事件只追加、可校验、可回放，并支持 SSE 断线续传。
5. 默认演示不依赖模型 API key 或高德 key，且连续运行三次得到相同业务结论。
6. 在线模式仍使用真实 hastekit 工具注册、模型调用、流式事件和 HITL。

## 2. 非目标

- 不实现完整 TMS。
- JSONL runtime 不支持多进程写入同一数据目录；服务必须用进程锁强制该限制。
- 不宣称本地日志与外部平台之间存在 exactly-once 事务。
- 本机演示模式不实现多租户；生产模式必须先接入身份、租户授权和共享持久化。
- 不让前端、HTTP handler 或大模型拥有业务状态。

## 3. 研究结论

hastekit v0.0.24 的源码核验结论如下：

1. `WithNeedsApproval(true)` 会让 Agent 在工具执行前保存 pending call，并返回
   `paused`。它不是阻塞 goroutine 的同步审批回调。
2. 调用方使用相同的 namespace 和 thread，再提交
   `FunctionCallInterruptResolutionMessage`，即可批准或拒绝并恢复执行。
3. `OpenFileHistory` 可以恢复已经持久化的 paused run。它不提供多进程协调。
4. SDK 自带 Workflow HTTP handler 只在内存中保存 checkpoint，进程重启会丢失。
5. retry 和 fallback 只处理模型调用。它们不替代写工具的业务幂等。
6. SDK 的流式 chunk 是实时信号，不是可靠审计源。慢消费者可能触发缓冲溢出。
7. 原生 OpenAI provider 请求 `BaseURL + "/responses"`。只有
   `/chat/completions` 的兼容服务必须使用 `openaicompat.Client`。
8. v0.0.24 对应 commit `df1bdd4560bcff6dbffea29a6e3a263cb8c39d44`，
   License 为 Apache-2.0，并要求 Go 1.25.3 或更高版本。

完整证据和源码链接见研究记录。

## 4. 总体架构

```text
web React
  |
  | HTTP + SSE
  v
cmd/server                 身份边界、协议转换、错误映射、SSE framing
  |
  v
internal/guardian          完整用例入口、run 串行、恢复协调
  |---- internal/agent     hastekit 组装、执行、暂停和恢复
  |       |---- internal/tools       七个 typed tools
  |       |          `---- internal/platform
  |       |                 |---- MockTMS / MockWeather / MockNotifier
  |       |                 `---- Real adapters
  |       |---- approval guard
  |       |---- idempotency middleware
  |       `---- audit middleware
  |
  |---- internal/approval  审批状态机和投影
  |---- internal/idempotency
  `---- internal/audit     唯一业务 JSONL、哈希链、replay 和 live

data/
  audit-<run_id>.jsonl      业务事实
  hastekit/                 SDK conversation 和 run_state
```

`guardian.Service` 是 HTTP 层唯一依赖的业务入口。它隐藏审批落盘、SDK resolution、
写操作去重和恢复顺序。HTTP handler 不直接协调这些步骤。身份验证和请求来源限制属于
`cmd/server` 边界；业务层只接受边界层提供的可信主体，不读取调用者自报的身份 header。

## 5. 调用方接口

```go
type Service interface {
    StartDemo(context.Context) (RunView, error)
    Decide(context.Context, ApprovalID, Decision) (ApprovalView, error)
    Timeline(context.Context, RunID, Seq) (Subscription, error)
    GetWaybill(context.Context, WaybillID) (WaybillView, error)
    Recover(context.Context) error
    Close() error
}
```

典型调用只有四步：

```text
POST /api/demo/trigger
  -> guardian.StartDemo
  -> 返回 run_id

GET /api/runs/:id/timeline
  -> guardian.Timeline
  -> 回放并持续推送已落盘事件

POST /api/approvals/:id/confirm
  -> guardian.Decide
  -> 先落盘决定，再在同一 run 锁内恢复同一 hastekit thread

GET /api/waybills/:id
  -> guardian.GetWaybill
  -> 返回地图所需的运单和轨迹
```

## 6. 状态所有权

| 状态 | 权威所有者 | 说明 |
|---|---|---|
| 模型消息、SDK step、pending tool call | hastekit file history | 只用于 Agent 恢复 |
| 审批请求、决定、过期时间 | `internal/approval` | 从业务日志重建内存投影 |
| 幂等 key、执行占用、首次结果 | `internal/idempotency` | 从业务日志重建内存投影 |
| run 生命周期、审计顺序、哈希链 | `internal/audit` | 每个 run 一份 JSONL |
| 外部副作用 | platform adapter 对应的系统 | 必须接受同一个幂等键 |
| 页面状态 | 无独立权威 | 从审计事件投影 |

approval 和 idempotency 不各写一份业务日志。两者把状态变化作为 typed event 追加到同一份
`data/audit-<run_id>.jsonl`，再从事件重建投影。这样一次业务事实只写一次。

hastekit history 与业务日志仍是两份物理记录。`guardian.Recover` 使用稳定 ID 对账，
不把两份文件描述成原子事务。

## 7. Run 与执行流程

Run 状态：

```text
started -> investigating -> awaiting_approval -> executing -> completed
                                           |-> rejected
                                           |-> failed
```

正常流程如下：

1. `StartDemo` 生成 `run_id` 和 `incident_id`，先追加 `run_started`。
2. 后台 worker 在 `namespace=waybill-demo`、`thread_id=run_id` 下执行 hastekit Agent。
3. Agent 依次调用四个只读工具。audit middleware 记录 `tool_call` 和 `tool_result`。
4. Agent 形成归因并记录 `attribution`。
5. Agent 生成改派和短信调用。SDK 在执行前暂停并持久化 pending calls。
6. `guardian` 把同一次 pause 的写调用组成一个不可变审批批次，追加
   `approval_requested`。
7. 人工确认后，`approval_decided` 先落盘。`guardian` 再向同一 thread 提交 approve
   resolutions。
8. 恢复后的写调用依次通过 approval guard 和 idempotency middleware，再进入 platform。
9. 全部写操作成功后记录 `approval_executed` 和 `run_completed`。
10. 人工驳回第一个改派方案后，Agent 提交候选运力二作为替代方案。第二次驳回才结束 run。

HTTP request context 只控制请求本身。已经接受的 run 使用服务生命周期 context，避免浏览器断开后
取消业务流程。进程关停时，HTTP 请求先收到服务 context 取消，SSE 等长连接退出；Engine 再
停止所有 AgentHandle，并等待已经进入工具函数的调用返回。最后才能关闭 history 和审计 store。

## 8. 工具契约与命名

`contract.yaml` 仍是七个工具的权威清单。Go 输入字段必须与其 `args` 一一对应。

工具名包含两种表示：

| 契约名 | 模型 wire name |
|---|---|
| `tms.get_waybill` | `tms_get_waybill` |
| `tms.get_tracking` | `tms_get_tracking` |
| `tms.get_driver` | `tms_get_driver` |
| `ext.get_road_weather` | `ext_get_road_weather` |
| `tms.reassign` | `tms_reassign` |
| `tms.create_claim` | `tms_create_claim` |
| `notify.send_sms` | `notify_send_sms` |

wire name 使用下划线，以兼容不同 OpenAI-compatible provider 的函数名限制。每个工具的
hastekit metadata 保存契约名和读写类型。启动校验必须检查：

- 恰好七个唯一工具。
- 四个只读工具设置 `ReadOnlyHint=true`，且不需要审批。
- 三个写工具设置 `RequiresApproval=true` 和 `IdempotentHint=true`。
- 写工具 schema 只包含业务参数，不包含 `effect_id` 或 `idempotency_key`。

`notify.send_sms` 的模型工具契约为：

```yaml
notify.send_sms:
  args: [waybill_id, recipient, carrier_id]
```

`recipient` 只允许 `shipper` 或 `driver`。服务端根据可信 `RunContext` 和严格解析的业务参数
生成 effect 身份和下游幂等键。审批通过后，handler 才查询当前联系方式、选择固定模板并组装
模板参数；模型和 history 不接触手机号、模板 ID 或参数映射。

## 10. 审批设计

一次 SDK pause 中的写调用组成一个 `Approval`：

```text
pending -> confirmed -> executed
        |-> rejected
        `-> expired
```

`executed` 只表示该审批包含的 effect 已全部获得成功结果。部分成功进入 `partially_failed`，
全部失败进入 `failed`。首次执行结果仍由
idempotency 投影持有。启动恢复发现“所有 effect 已成功但审批仍 confirmed”时，会补写
`approval_executed`。

审批单包含：

- `id`、`run_id`、`waybill_id`
- `items[]`，每项含 `call_id`、契约 action、脱敏参数、参数哈希、effect ID 和幂等键
- `reason`、`evidence`
- `status`、`requested_at`、`expires_at`
- `decided_by`、`decided_at`、`reject_reason`

审批 ID 从 `run_id + sorted(call_id)` 派生。同一次 pause 被重复观察时返回原审批。
确认、驳回和过期在同一个 run 锁内做条件状态迁移：

- 相同决定重复提交返回当前状态。
- 相反决定返回 HTTP 409。
- 驳回原因不能为空。
- 超时默认拒绝，并向 SDK 提交 reject resolution。
- 已确认参数用 canonical hash 绑定。恢复执行时参数不匹配则拒绝写入。

`guardian.Service` 为每个 pending 审批维护一个可取消定时器。新审批和启动恢复出的未到期审批
都会注册定时器；确认、驳回或服务关闭会取消对应定时器。定时器到期与人工决定竞争同一个 run
锁，因此只有一种决定能落盘和恢复 SDK。

## 11. 幂等设计

模型只提交写操作的业务参数，不提交 `effect_id` 或 `idempotency_key`。`guardian` 在把 paused
tool call 物化为审批项时，先按 action 对参数做严格解码和校验，再生成稳定身份。

当前 JSONL 模式使用 `effect-v1` 算法：

```text
proposal_id = UUIDv5(
  proposal_namespace,
  canonical_json(run_id, incident_id, waybill_id, plan_version)
)

arguments_hash = SHA256(canonical_business_arguments)

proposal_item_id = SHA256(canonical_json(
  identity_version,
  action,
  target,
  arguments_hash
))

effect_id = UUIDv5(
  effect_namespace,
  canonical_json(proposal_id, proposal_item_id)
)

idempotency_key = SHA256("waybill-effect-key-v1\0" + effect_id)
```

`target` 由服务端按 action 从已校验参数中提取：改派使用运单和目标承运商，理赔使用运单和
理赔类型，短信使用接收手机号。参数对象的字段顺序和 `params` map 的键顺序不影响身份。
未知字段会被拒绝，因此模型不能伪造执行字段。

同一提案中，action、target 和业务参数完全相同的两项得到相同 `proposal_item_id`，服务端在
写入 `approval_requested` 前拒绝整批提案。相同 action 但目标或参数不同的两项得到不同
`effect_id`，分别执行和记录结果。

审批项持久化 `identity_version`、`effect_id`、业务参数哈希和下游幂等键。hastekit 的
`call_id` 只用于 pause/resume 和审批调用关联，不参与 effect 身份计算。确认后，effect
middleware 根据原始业务参数重算身份，并与审批项比较。校验通过后，middleware 通过可信
execution context 把幂等键交给 typed handler；SDK history 和模型参数中不保存该 key。

执行状态：

```text
absent -> started -> succeeded
                  |-> failed
                  `-> indeterminate
```

同 key 并发调用由单进程 keyed entry 合并。一个调用执行，其余等待首次结果。成功结果持久化后，
后续调用直接回放结果并记录 `duplicate_suppressed`。每次确定失败后的重试使用递增 attempt，
`write_started` 和结果事件 ID 同时包含 `effect_id` 与 attempt，避免 append-only 事件去重
误吞后续尝试。

本地 JSONL 无法与外部 TMS 原子提交。若进程在“平台成功、结果落盘前”退出，恢复只能用相同 key
重试或查询。因此真实 adapter 必须支持下游幂等键或按 key 查询结果，否则禁止启用真实写模式。

历史 schema-v1 审批项没有 `identity_version` 和 `effect_id`。重放时保留其已审批的原
`idempotency_key` 和包含该 key 的参数哈希，不从脱敏后的展示参数推导新身份。已有成功结果只
回放，不再次调用 platform。若一个未完成的旧审批中有两个 item 共用同一 key，恢复在任何外部
调用前失败并要求重新发起方案。审计 envelope 和哈希算法保持 schema version 1；新增身份字段
只出现在 payload 中。

PR #45 短暂写入过只有 `effect_id`、没有 `identity_version` 和 `attempt` 的 `effect-v0` 记录。
恢复时按该版本的 UUIDv5 和 key 算法重算并校验身份，只回放已有成功结果。新审批不再生成
`effect-v0`。

## 12. 审计与 JSONL

事件模型：

```go
type Event struct {
    SchemaVersion int             `json:"schema_version"`
    EventID       string          `json:"event_id"`
    Seq           uint64          `json:"seq"`
    TS            time.Time       `json:"ts"`
    RunID         string          `json:"run_id"`
    Actor         string          `json:"actor"`
    Type          string          `json:"type"`
    Payload       json.RawMessage `json:"payload"`
    PrevHash      string          `json:"prev_hash"`
    Hash          string          `json:"hash"`
}
```

事件类型包括：

`run_started`、`tool_call`、`tool_result`、`attribution`、
`approval_requested`、`approval_decided`、`approval_executed`、
`write_started`、`write_executed`、`write_failed`、
`duplicate_suppressed`、`run_completed`、`run_rejected`、`run_failed` 和 `note`。

每个 run 使用一份 `data/audit-<run_id>.jsonl`。append 在该 run 的锁内完成：

1. 校验预期序号和稳定 `event_id`。
2. 在哈希前完成字段脱敏。
3. 计算 `seq`、`prev_hash` 和 `hash`。
4. 一次写入完整 JSON 和换行。
5. 调用 `fsync`。
6. 更新内存投影并通知订阅者。

`hash` 使用 SHA-256，输入是版本化的固定字段 JSON，不包含 `hash` 本身。首条事件的
`prev_hash` 是 64 个 `0`。回放校验 seq 连续、`prev_hash` 和当前 `hash`。

启动时可以截断最后一条不完整记录。中间坏行、序号倒退或哈希不匹配必须启动失败。
手机号和车牌在写入审计前脱敏。

JSONL runtime 在打开数据目录时必须：

1. 将数据目录和 `hastekit/` 目录权限收紧为 `0700`。
2. 对数据目录的打开文件描述符获取非阻塞进程级独占锁，并持有到 `Service.Close`。
3. 已有 writer 持锁时拒绝第二个服务实例启动。
4. 继续以 `0600` 创建业务审计文件。

直接锁定目录 inode，并相对该目录文件描述符枚举、打开和创建日志。即使目录路径被重命名或
替换，当前 Store 也只操作持锁的原目录。进程锁只是在本地 runtime 中强制单 writer，不是
生产多实例协调。生产模式必须改用事务存储、唯一约束和带 fencing token 的 run lease。

SDK history 只保存工具层提供的业务证据白名单。统一 guard 在模型调用和持久化边界拒绝
手机号、车牌、精确坐标和短信供应商参数。本地 history 使用 `0600` JSONL 与版本 sidecar；
PostgreSQL history 使用 AES-256-GCM 加密 payload。两种后端都只按 `HISTORY_RETENTION`
删除过期终态 history，业务审计不参与该清理。

## 13. SSE 协议

SSE 帧使用持久化事件：

```text
id: <seq>
event: <event.type>
data: <完整 Event JSON>
```

`Last-Event-ID` 是当前 run 内最后成功处理的 `seq`。服务端返回所有 `seq > cursor` 的事件。
`Timeline` 在同一锁内复制 backlog 并注册 live subscriber，避免 replay 与 live 之间丢事件。
传输层允许重复，前端按 `(run_id, seq)` 去重。

非法游标返回 400，未知 run 返回 404，游标超过当前末尾返回 409。服务端每 15 秒发送无 ID
的 comment heartbeat。慢消费者断开后依靠 `Last-Event-ID` 重连，不阻塞日志 writer。

此行为符合 WHATWG Server-Sent Events 的事件 ID 和自动重连模型：
<https://html.spec.whatwg.org/multipage/server-sent-events.html>。

## 14. 演示模式与在线模式

默认 `AGENT_MODE=demo` 使用确定性 fixture provider。provider 只实现 Agent 使用的
Responses 路径，其他能力返回明确的不支持错误。它根据持久化 conversation 中已有的工具结果
决定下一步，不使用进程内 step counter。

默认模式仍经过真实 hastekit Agent loop、七个真实工具、HITL、middleware、file history
和流式事件，只替换外部模型调用。因此默认演示不需要 API key，也能验证 SDK 接线。

`AGENT_MODE=online` 才读取模型配置：

- `LLM_API_STYLE=responses` 时，使用 hastekit OpenAI provider。
- `LLM_API_STYLE=chat_completions` 时，使用 SDK 内部基于 `openaicompat.Client`
  的 OpenAI-compatible bridge。
- `LLM_API_KEY` 和 `LLM_MODEL` 必填。
- `LLM_BASE_URL` 指向 API 根路径，通常包含 `/v1`，且不包含具体 endpoint。
- `LLM_BASE_URL` 必须是绝对 HTTP(S) URL，不接受末尾 `/`、`/responses` 或
  `/chat/completions`，避免 SDK 拼接出错误地址。
- 在线模式安装一次 hastekit model retry，默认最多三次。当前配置只有一个 provider，
  因此不安装也不宣称 fallback；增加第二个独立 provider 后才能配置 fallback。

## 15. HTTP 与前端

### 15.1 当前身份边界

当前版本只有 `local` 运行模式：

- `HTTP_ADDR` 默认是 `127.0.0.1:8080`。
- 监听地址必须使用 loopback IP 字面量。空 host、主机名、通配地址和非 loopback 地址都拒绝启动。
- HTTP 请求的 `Host` 也必须使用 loopback IP 字面量，阻断浏览器 DNS rebinding。
- `PLATFORM=real` 继续拒绝启动。
- 审批人固定为受信任的本机演示主体 `local-demo-reviewer`，HTTP 层忽略并删除
  调用者提供的 `X-Actor`。

这组限制用于封闭当前无认证 demo 的网络边界，不等同于生产鉴权。

生产模式的目标接口是：

```go
type Principal struct {
    Subject  string
    TenantID string
    Roles    []Role
}

type Authenticator interface {
    Authenticate(*http.Request) (Principal, error)
}

type Authorizer interface {
    CanAccessWaybill(context.Context, Principal, WaybillID) error
    CanAccessRun(context.Context, Principal, RunID) error
    CanDecideApproval(context.Context, Principal, ApprovalID) error
}
```

生产入口必须验证 OIDC/JWT 的 issuer、audience、签名和时效，并从已验证 claims 构造
`Principal`。run、approval 和 waybill 都要绑定 `tenant_id`；服务不能只凭资源 ID 授权。
SSE 与普通 HTTP 使用同一会话身份。生产身份适配器和租户字段完成前，不允许开放非 loopback
监听，也不允许启用真实 platform adapter。

HTTP 端点：

| 方法 | 路径 | 成功响应 |
|---|---|---|
| POST | `/api/demo/trigger` | 202，返回 `run_id` 和 `waybill_id` |
| GET | `/api/runs/:id/timeline` | SSE |
| POST | `/api/approvals/:id/confirm` | 202，返回最新审批 |
| POST | `/api/approvals/:id/reject` | 202，返回最新审批 |
| GET | `/api/waybills/:id` | 200，返回运单、轨迹和风险 |
| GET | `/healthz` | 200 |

错误统一为 `{"error":{"code":"...","message":"..."}}`。请求体拒绝未知字段。

前端是物流运营操作台，不是营销页。首屏包含：

1. 运单摘要和风险评分。
2. 高德轨迹地图，绵阳异常点高亮，点击点显示时间和速度。
3. 审计时间线和回放控制。
4. 一屏内可读完的审批卡片。

时间线 reducer 是页面状态的唯一来源。无高德 key 或 SDK 加载失败时，地图区域显示本地坐标轨迹
和配置提示，其他功能继续工作。

## 16. 恢复矩阵

| 崩溃位置 | 恢复动作 |
|---|---|
| `run_started` 后、`approval_requested` 前 | 本地 runtime 没有可证明安全的业务检查点，记录失败并由调用方重新触发；此阶段没有写副作用 |
| `approval_requested` 已写、仍 pending | 未到期则重挂定时器；已到期则落盘 expired 并提交 reject resolution |
| confirmed 已写、resolution 未送达 | 重发 approve resolution；已成功的 effect 由 middleware 回放 |
| rejected / expired 已写、resolution 未送达 | 若没有后续审批或终态事件，重发 reject resolution |
| write 已 started、结果未知 | 不自动重试；返回 indeterminate 并要求真实平台按 key 对账 |
| 平台成功、结果未写 | 同上；仅在真实平台确认结果或证明同 key 重试安全后人工恢复 |
| write 结果已写、SDK 未保存 tool result | 重发 approve resolution，middleware 回放首次结果 |
| run 已完成、approval_executed 未写 | 所有审批 effect 均有成功结果时补写 approval_executed |
| 事件已落盘、SSE 未发送 | 客户端重连后回放 |

恢复器只重放已经落盘的人类决定，永远不会自动批准 pending 审批。恢复操作按 run 串行且幂等；
同一进程多次调用 `Recover` 不会重复副作用。上述能力是初赛本地 runtime 的边界，生产环境仍需
Temporal 或 Restate 处理任意 Agent step 的持久恢复。

## 17. 测试与验收

必须覆盖：

- 七个工具 descriptor、字段、读写注解和审批标志与 `contract.yaml` 一致。
- 真实 hastekit Agent 在写工具前 paused，恢复后只执行一次。
- 审批合法状态、非法跳转、重复决定和超时。
- 同 key 并发十次只进入 platform 一次。
- 十条事件的回放顺序、脱敏和哈希链。
- JSONL 最后半行修复，中间损坏时拒绝启动。
- SSE 断线后按游标补齐，replay/live 交接不漏事件。
- 无模型 key、无高德 key 时完整流程可运行。
- 改派被驳回后产生候选运力二方案。
- 同一服务进程连续运行三次，每个 run 只有一次改派和一次短信副作用。
- `go test -race ./...`、`go vet ./...`、`go build ./...`、`npm test`、`npm run build`、
  `npm audit` 和 `npm run verify:e2e` 全部通过。

## 18. 演进路径

生产化按可独立验证的阶段推进：

1. **本机安全基线**：限制 loopback、删除自报审批人、收紧数据目录权限、强制 JSONL 单 writer。
2. **副作用一致性**：服务端生成带 `effect_id` 的幂等键；记录每次 attempt；区分确定失败、
   未知结果和部分成功；提供对账状态机。
3. **身份与租户**：接入 OIDC/JWT、RBAC 和对象级授权；为 run、approval、waybill 和审计事件
   增加 `tenant_id`。
4. **生产持久化**：用 PostgreSQL 事务表替换 JSONL，以唯一约束、outbox、run lease 和
   fencing token 支持多实例。
5. **运行恢复与操作面**：用 Temporal 或 Restate 承接 durable runtime；提供 active run、
   pending approval、reconciliation 列表和恢复 API。
6. **实时与运维**：用 Redis 或消息系统分发 SSE；增加速率限制、写超时、指标、追踪、告警、
   部署清单和灾备演练。

每个阶段必须单独提交、测试和评审。阶段 2 完成前不启用真实写 adapter；阶段 3 和阶段 4
完成前不开放多租户或多实例部署。

## 19. 设计选择记录

选定方案以 `guardian.Service` 为业务入口，以每个 run 的单一 JSONL 为业务事实源，
并保留 hastekit file history 作为 SDK checkpoint。该方案满足 issue 的 JSONL 要求，
同时避免 approval、idempotency 和 audit 各自写盘造成的多份业务事实。

未采用的方案：

- SQLite 是更合适的生产存储，但不符合初赛 issue 的 JSONL 验收。
- 多份 package-local JSONL 会把提交顺序和补偿逻辑暴露给编排层。
- 把业务状态塞入 hastekit history 会让审批和审计依赖不稳定的 SDK 内部格式。
- 阻塞 goroutine 等待审批会重复实现 SDK 已有的 pause/resume，并且不能抗进程退出。

当前取舍是使用单进程锁、每次 append 执行 `fsync`，并用恢复对账处理业务日志、SDK history
和外部副作用之间不可避免的边界。
